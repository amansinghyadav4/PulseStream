# 1. Project Identity

**Name:** PulseStream

**Type:** Real-Time Event Processing & Analytics Platform

**Primary engineering focus:**
- Distributed systems
- Event-driven architecture
- Kafka
- Real-time processing
- Backend engineering
- Redis
- PostgreSQL
- WebSockets
- Docker
- Observability
- Performance/load testing
- Cloud deployment

## Core problem

Modern applications continuously generate events:

- user login
- page view
- product view
- order created
- payment completed
- payment failed
- shipment updated
- service events
- application events

PulseStream provides an infrastructure-style pipeline for ingesting, processing, storing, aggregating, and visualizing these events in near real time.

The main engineering question is:

> How can we reliably process a high volume of application events asynchronously while providing real-time analytics to users?

PulseStream is primarily a **distributed event-processing system**, not an AI project and not an incident-management platform.

---

# 2. Product Goals

## Primary goals

1. Accept application events through an API.
2. Validate and normalize incoming events.
3. Publish events to Kafka.
4. Process events asynchronously using Kafka consumers.
5. Support consumer groups and horizontal worker scaling.
6. Persist important event data in PostgreSQL.
7. Use Redis for low-latency counters/caching where appropriate.
8. Calculate real-time analytics.
9. Push dashboard updates through WebSockets.
10. Provide health and operational visibility.
11. Support graceful failure and retry behavior.
12. Benchmark throughput and latency.
13. Containerize the system using Docker.
14. Provide a clear path to AWS deployment.

## Non-goals

PulseStream is NOT:

- an AI chatbot
- a RAG application
- an ML anomaly detector
- a replacement for Kafka
- a generic CRUD dashboard
- an unnecessarily complex microservices demonstration

# 5. Event Schema

Initial canonical event:

```json
{
  "event_id": "uuid",
  "event_type": "order.created",
  "source": "checkout-service",
  "timestamp": "ISO-8601 timestamp",
  "user_id": "optional-id",
  "request_id": "optional-id",
  "payload": {},
  "schema_version": 1
}
```

Important properties:

- `event_id` must be unique.
- `event_type` identifies the event.
- `source` identifies the producer/service.
- `timestamp` should be normalized.
- `schema_version` allows future evolution.
- Payload should be validated according to event type where practical.

Do not store unnecessary PII.

---

# 6. Kafka Design

Kafka is the core distributed event backbone.

## Initial topic strategy

Use a small number of meaningful topics rather than one topic per event type.

Example:

```text
application-events
analytics-events
dead-letter-events
```

The final topic strategy must be documented after implementation.

## Partitioning

Partitioning must be based on an explicit key.

Potential key:

```text
user_id
```

or, for service-centric workloads:

```text
source
```

The choice must be justified based on ordering and load distribution requirements.

## Consumer groups

At least two logical consumer groups should exist:

```text
analytics-workers
persistence-workers
```

This demonstrates that multiple downstream consumers can independently process the same event stream.

---

# 7. Processing Semantics

The system should target **at-least-once processing** initially.

This means duplicate delivery is possible.

Therefore the application must use idempotency where required.

Example:

```text
event_id
   ↓
check processed state
   ↓
already processed? → skip safely
   ↓
not processed
   ↓
process
   ↓
persist/update state
```

Do not claim exactly-once semantics unless it is actually implemented and demonstrated.

---

# 8. Failure Handling

The system should explicitly handle:

- Kafka unavailable
- PostgreSQL unavailable
- Redis unavailable
- worker crash
- malformed event
- duplicate event
- transient processing failure
- permanent processing failure
- WebSocket client disconnect

Initial retry strategy:

```text
consume
  ↓
process
  ↓
failure?
 ├── transient → retry
 └── permanent → dead-letter topic
```

Do not endlessly retry poison messages.

---

# 9. Redis Responsibilities

Redis should have a clear purpose.

Potential uses:

- real-time counters
- short-lived aggregation state
- dashboard cache
- rate limiting
- idempotency metadata where appropriate

Example counters:

```text
events_processed_total
events_failed_total
events_by_type
events_by_source
events_per_minute
```

Avoid using Redis as the permanent source of truth.
